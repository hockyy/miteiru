## Manual notes

**A6 visual check (screenshots in the scratchpad `spike-logs\shots`, viewed by hand):** libass@14s shows the yellow sign at the top (libass, with the \pos and fade) and the dialogue at the bottom, inside the video. hybrid@14s shows the same libass sign plus the DOM overlay dialogue, exactly one dialogue line (the signs-only track carries no dialogue). overlay@2s shows 今日はいい天気ですね。 as clickable word spans. Note the test video has a yellow bar behind the sign, so the colour census in the JSON is not meaningful; the screenshots are the evidence. A6 = PASS.

**What worked first try:** the zero-copy path. A D3D11 device on the adapter matching Chromium's active GPU, BGRA SHARED|SHARED_NTHANDLE textures, `Flush` + `D3D11_QUERY_EVENT`, then `importSharedTexture` + `sendSharedTexture` + `getVideoFrame()` + canvas `drawImage` worked on Windows with no garbage or tearing. Electron's ntHandle is an 8-byte little-endian Buffer holding the HANDLE value (probe of an offscreen `useSharedTexture` window: `440d000000000000`). Electron does not close or invalidate our long-lived handle; the same handle is re-imported every frame for the life of the ring.

**Sync variant:** `query` (SHARED + SHARED_NTHANDLE, Flush + event query) worked and is the default. `keyedmutex` (SHARED_KEYEDMUTEX + AcquireSync/ReleaseSync(0)) also worked with identical fps and drops, so the keyed mutex is not needed. Neither showed torn or garbage frames.

**Render path numbers:** all tables are zero-copy; no copy fallback was built. Canvas 2D drawImage already holds 4K60 (99.8%), so WebGPU importExternalTexture is not needed (it also works: 99%, 16 drops / 1 stall, slightly worse in this run).

**Things I changed while building (vs. the brief):**
- `app.getGPUInfo('basic')` reports `active:false` for every device on this machine; the harness falls back to `'complete'`, which marks the NVIDIA GPU active (Chromium runs on the 4070 Ti SUPER).
- mpv does not auto-select the embedded ASS track here (no default flag, no slang), so the harness sets `sid=1` after `file-loaded` for libass/overlay.
- The first version called `mpv_render_context_render` with `BLOCK_FOR_TARGET_TIME=0` to measure pure render time (1.6-3.9 ms average). Review turned it back on (option `blockForTargetTime`, now default true): render.h warns that without our own frame timing, A/V sync ends up slightly off. The render call now waits for each frame's display time, so the player's `avgRenderMs` (about 41.6 ms at 23.976 fps, 16.6 ms at 60 fps) is mostly that wait. fps and drops did not change.
- `destroy()` returns a Promise (napi AsyncTask) because it waits up to 1 s for slot releases that are delivered on the JS thread. Slot tokens are opaque (ring generation << 8 | index) so a late release from an old ring cannot free a slot of a new one.
- Extra napi methods: `adapterInfo()`, `stats()`; extra options `sync`, `blockForTargetTime`.
- `mute=yes` is set so the test PC stays quiet; audio still decodes (DTS to AC3 switch verified through `audio-codec-name`).

**Changes made in review:**
- `BLOCK_FOR_TARGET_TIME` is back on by default (see above).
- The render thread no longer calls `mpv_get_property`. render.h forbids non-render libmpv calls on the render thread (deadlock risk), so the ring size now comes only from the observed `dwidth`/`dheight`.
- The harness takes its work folder from `SPIKE_S` instead of a machine-specific default, and `gen-media.sh` plus `subs-ja.ass` make the test media reproducible (see README.md).
- The crates carry no `license` field: the repo is CC BY-NC-SA 4.0, and choosing a licence for the shared core is the owner's call.

**Known issues / observations:**
- The first 1-3 frames are dropped at start (frame-drop-count 1-3 over a run): the first render takes 120-160 ms (mpv shader setup on the D3D11 backend). Total drop rate stays 0.2-0.6%.
- Hi10P H.264 (`hi10p1080-h264-10bit-ac3-ass.mkv`) runs on software decode (hwdec `no`): the NVIDIA decoder rejects H.264 High10 ("Hardware is lacking required capabilities"); it still plays at 100% of source fps; mpv decodes in-process so the software decode cost lands in the Browser column (0.8%, per-core average; not separately verified).
- Adapter mismatch (x-base-intel row): mpv's device on the Intel iGPU while Chromium runs on NVIDIA. Imports and sends do not error, but only the first 3 frames (ring size) are ever drawn: slots are never released, then the render thread stalls (50 stalls, 0 fps). So a wrong adapter is a silent hang, not an exception; adapter matching is mandatory. (The player log wording "matched Chromium's GPU" in that row just means "matched the requested adapter".)
- CPU% columns look tiny because the decoding and rendering happen on the GPU and in mpv threads inside the browser process while Electron's `percentCPUUsage` is per core and averaged per second; they are comparable between rows but are not a whole-system figure.
- html mode: baseline plays (99.7%, 0 dropped). hard1080 (HEVC 10-bit in MKV with DTS) also plays in Electron 41's `<video>` on this machine (HEVC hardware decode is available); the harness mutes the video so audio support (DTS/AC3) was not checked, and the multi-audio-track switch and ASS styling are not available in `<video>`.
- sub-text while hidden: `sub-text` keeps updating with `sub-visibility=no` (9 property events in 20 s, one per cue plus empty strings). In overlay mode the Sign event is merged into the dialogue (text "この映画はとても面白かった。
看板：喫茶店"): positioning, colour and fade of signs are lost, which is why hybrid (libass for signs, overlay for dialogue) is the right split.
- Overlay font: libass sizes Fontsize so that ascent+descent equals it; for Noto Sans JP the CSS font-size must be 64/1.448 of the PlayRes-scaled size to match libass (done in `renderer.js`).
- Shutdown: close to exit took up to about 1.5 s, always with code 0 and no leftover processes. The slower ones (over 1 s) are the runs where Chromium had not released all slots when the window closed, so `destroy()` waited its 1 s.
- Not tested: HDR/tonemapping, window resize while playing (the ring resize path was only exercised at startup), pause/seek stress, more than one player.
